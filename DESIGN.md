# dsh-peak-guard — проект

**Публикация: GitHub + маркет-индекс, без npm.** Репозиторий
`github.com/machine202502/dsh-peak-guard`, в индексе `dsh-restart` — git-источник с пином
на коммит, как у `dsh-pricing`. Пакета в npm нет и не будет: publish-workflow в репозитории
не создаём.

## 1. Что делает

Пиковый тариф DeepSeek дороже вдвое. Расширение следит за расписанием пика и, если сессия
работает, само пишет в чат: «наступил пик, до такого-то часа, сворачивайся» — и в конце пика
само возвращает агента к работе.

1. **Включение по сессии.** В шапке сессии кнопка-чип. Пока не включишь — молчит.
2. **Уведомление на старте пика** — только если сессия реально работает (агент `running`),
   с просьбой притормозить и указанием, когда пик кончится.
3. **Возврат после пика** — steering сразу, в том же процессе, без ожидания простоя.

Не входит: считать деньги, показывать цены, управлять провайдерами, трогать субагентов,
отменять работу агента.

## 2. Как это выглядит

```
[чип «ПИК» в шапке сессии]  выкл → вкл
...
06:00  →

⏳ Пиковый тариф, до 09:00 (через 3 ч).
   Приостановь то, что можно продолжить позже; доведи до конца только то, что
   почти готово. Коротко скажи, на чём остановились.
   В 09:00 вернусь к работе сам.

09:00  →

▶️ Пик закончился, тариф снова половинный. Продолжи то, что приостановил.
```

## 3. Принятые решения

### D1. Откуда берётся расписание

**Источник — бридж `dsh-pricing`**: `GET http://127.0.0.1:38037/state`, поле `peak`
(`windows`, `tz`, `days`, `holidays`). Он уже тянет официальную страницу цен каждые 6 часов,
валидирует и кэширует её; второй парсер — второй источник правды.

Запасной вариант: копия окна в конфиге (`fallbackPeak`), если бридж недоступен. В лог —
одна строка `peak source: fallback`, в чат ничего.

Отвергнуто: свой фетч страницы (дублирование), хардкод в коде (нельзя поменять без правки).

### D2. Как сообщение попадает в чат

Хост-сторонний плагин, `ctx.agents`:

- **старт пика**: если `agent.status === 'running'` → `agent.steer(createUserMessage({...}))`.
  Steering попадает в ближайшую границу шага, не открывая новый ход: агент дочитывает
  текущий шаг и видит просьбу свернуться. Если `idle` — не будим, держим «долг» и отдаём
  steering на ближайшем переходе `idle → running` внутри того же окна, один раз.
- **конец пика**: `agent.steer(...)` **всегда**. У спящего агента steer сам открывает ход
  («an idle driver starts a turn»), у работающего — вклинивается в ближайший шаг. Это и есть
  «проснуться после пика», без ожидания простоя.

`followup` не используем: он открывает отдельный ход и выглядит как новый запрос пользователя.
`inject` не используем: в транскрипте не видно, а нужно именно уведомление.

### D3. Возврат после пика: свой таймер, не Schedule

Решение поменялось после твоего ответа: Schedule доставляет в сессию только когда она
устаканилась (`hold their execution slot until the target Agent becomes idle`), то есть
вклиниться в идущую работу им нельзя. А ты просил вклиниваться сразу.

Поэтому:

- плагин держит таймер на границу окна и в конце пика делает `steer` сам;
- долговечность — не через Schedule, а через файл состояния: перед пиком пишем
  `resumePending: { at, delivered }`, после доставки ставим `delivered: true`;
- при старте плагина проверяем: если `resumePending` просрочен и доставлен не был —
  доставляем сразу («пик кончился, продолжай»), даже если DSH был закрыт всё это время.

Отвергнуто: schedule-задача на конец окна (не вклинивается, ждёт простоя; плюс лишняя запись
в «Automation tasks»); таймер без файла состояния (рестарт DSH его теряет).

### D4. Тумблер

Клиентская кнопка-чип в слоте `conversation.session.header.utilities` — там же, где чип
`dsh-pricing`. Вид: «ПИК» с точкой: серая — выключено, синяя — следит.

Клик ходит в локальный бридж плагина (`127.0.0.1:38038`), тот пишет состояние. Схема та же,
что у `dsh-pricing`: клиентская половина не имеет прямого доступа к сессии хоста.

Состояние — `%LOCALAPPDATA%\dsh-peak-guard\sessions.json`:

```json
{
  "session-...": {
    "enabled": true,
    "windowStart": "2026-11-16T06:00:00.000Z",
    "notified": true,
    "resumePending": { "at": "2026-11-16T09:00:00.000Z", "delivered": false }
  }
}
```

### D5. Таймер

Один `setTimeout` на ближайшую границу, пересчёт после каждого срабатывания и после каждого
обновления расписания. Плюс страховка: пересчёт при `agent/status → running`.

### D6. Сигнала «пик кончается через 15 минут» не будет

Он решает только одну задачу — дать агенту время подготовиться к продолжению (прогреть сборку,
перечитать состояние) или не оборвать длинный шаг. Наш сценарий в этом не нуждается: на старте
пика агент уже свернулся, а на конце — получает steering и продолжает с того же места.
Лишний сигнал = лишний токен-расход и ещё одно сообщение в транскрипте.

## 4. Устройство

```
dsh-peak-guard/
├── index.js           хост: расписание, таймер, доставка, бридж, настройки
├── client.js          кнопка в шапке сессии + карточка настроек языка
├── cordis.patch.yml   одна строка: id: peak-guard, name: '@machine202502/dsh-peak-guard'
├── locale/            ru/en/zh — название и описание в списке плагинов
├── docs/img/          скриншоты для README
├── package.json       public-репозиторий, publishConfig не нужен, npm-скриптов нет
├── icon.svg
├── README.md          что делает, как включить, ограничения
├── README.ru.md
└── DESIGN.md
```

Хостовые зависимости (все есть в 0.2.2-rc.1):

| Что | Откуда | Зачем |
|---|---|---|
| `ctx.agents` | `@deepseek-ai/dsh-agent` | `get(sessionId)`, `status`, `steer()` |
| `createUserMessage` | `@deepseek-ai/dsh-llm` | сборка сообщения |
| `agent/status` | событие | переход `idle → running` для «долга» |
| `node:http` | встроенный | бридж для кнопки |

HTTP-клиент к бриджу цен — `fetch` с таймаутом 2 с; недоступность не ошибка, а повод взять
`fallbackPeak`.

## 5. Алгоритм

```
старт плагина
  ├─ читаем состояние, чистим записи для несуществующих сессий
  ├─ читаем расписание (бридж, иначе fallbackPeak)
  ├─ догоняем просроченный resumePending (доставляем, если не доставлен)
  └─ arm()

arm()
  ├─ если сейчас внутри окна пика и есть включённые running-сессии без notified
  │     → notify(sessionId) сразу
  └─ таймер на ближайшую границу: старт следующего окна или конец текущего

граница «старт окна»
  ├─ перечитываем расписание
  ├─ для каждой включённой сессии:
  │     ├─ running → steer(«пик начался»), notified = true, resumePending = {at: end}
  │     └─ idle    → ничего, notified = false (долг)
  └─ arm()

граница «конец окна»
  ├─ для каждой включённой сессии:
  │     ├─ notified или resumePending → steer(«пик кончился»), resumePending.delivered = true
  │     └─ иначе → ничего
  └─ arm()

agent/status → running
  └─ если сессия включена, идёт окно пика, notified = false
        → steer(«пик уже идёт, до …»), notified = true, resumePending = {at: end}
```

`notified` сбрасывается на конце окна.

## 6. Тексты

Русский по умолчанию, `language` в конфиге: `ru` | `en`. Источник сообщения —
`{ kind: 'peak-guard' }`, чтобы в транскрипте было видно, что это плагин.

**Старт пика:**

> ⏳ Пиковый тариф, до {end} ({left}).
> Приостановь то, что можно продолжить позже; доведи до конца только то, что почти готово.
> Коротко скажи, на чём остановились.
> В {end} вернусь к работе сам.

**Долг (пик уже идёт, сессия проснулась):**

> ⏳ Идёт пиковый тариф, до {end} (осталось {left}).
> Дальше — по возможности короче: не начинай длинные шаги, доведи текущее.
> В {end} вернусь к работе сам.

**Конец пика:**

> ▶️ Пик закончился, тариф снова половинный. Продолжи то, что приостановил.

## 7. Краевые случаи

| Случай | Поведение |
|---|---|
| Ценовой плагин выключен | `fallbackPeak` из конфига + строка в лог; нет и его — чип показывает «нет данных», уведомлений нет |
| Праздники Китая | `holidays` в бридже пуст → в праздник будет ложное «пик»; пишем в README, лечится заполнением дат |
| Окно через полночь | сравнение минут с переносом через 00:00 |
| Два окна в день | обрабатываются независимо, своё `notified` на каждое |
| Сессия занята в конце пика | steering вклинивается в ближайший шаг — не ждём простоя |
| Сессия спит в конце пика | steer сам открывает ход, агент продолжает |
| DSH выключен в конце пика | при старте `resumePending` просрочен и не доставлен → доставляем сразу |
| DSH выключен, к старту уже новый пик | просроченный resume отбрасываем (`delivered: true`, без сообщения): идёт новый пик, сворачиваться нужнее |
| Тумблер выключили в середине пика | `resumePending` чистим, на конец окна не реагируем |
| Сессия заархивирована | `ctx.agents.get` вернёт `undefined` — просто пропускаем, состояние чистим |
| Субагенты | уведомление только в корневую сессию |
| Пользователь сам поставил задачу в пик | не мешаем: одно сообщение на окно |

## 8. Проверка

Без ожидания настоящего пика: конфиг `debugWindows` — окно на две минуты вперёд,
`debugTz` — локальная зона. Включаешь в сессии, просишь агента что-нибудь делать, через
минуту приходит steering, ещё через минуту — «продолжай», вклинившееся в идущий шаг.

Утверждения:

1. Чип появляется в шапке, состояние переживает перезапуск DSH.
2. `running` в начале окна — ровно одно сообщение; `idle` — ни одного.
3. Проснувшаяся в пике сессия получает «долг» один раз.
4. В конце пика steering приходит в идущую работу, не дожидаясь простоя.
5. Плагин, выключенный на время пика, при старте догоняет просроченный resume.
6. Выключение тумблера в пике снимает `resumePending`.
